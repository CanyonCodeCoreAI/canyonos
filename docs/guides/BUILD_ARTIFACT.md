# The `.car` artifact

A `.car` directory holds everything CanyonOS needs to deploy an application:
a copy of the source, the manifest, and one yaml declaration per agent. It
sits next to the application source, and the source itself is not part of the
deployment.

## Names

CanyonOS Core is the product. `canyonos` is the CLI. Inside the platform the
Python package is `canyonos_core`, environment variables start with
`CANYONOS_`, and Docker images and containers are named `canyonos-*`. Image
tags are the lowercased entry name (`canyonos-splitagent`), and containers are
`canyonos-<agent>-<replica>`.

## Layout

```text
.car/
  config/
    global_controller.yaml   deployment manifest
    policy.yaml              optional access rules
    <name>.yaml              one declaration per agent service
  app/                       copy of the application source, becomes /app
  stubs/                     generated by the build
  grpc_stubs/                generated by the build
  docker_container/          generated by the build, one context per image
```

You author `config/` and `app/`. `canyonos deploy` writes the other three
next to them, never inside `app/`. `canyonos clean` deletes the whole `.car`,
including `app/` and `config/`, and removes every local Docker image named
`canyonos-*`.

Every path in the manifest (`entrypoint`, `workflow_file`) is relative to
`app/`. It has to be a `.py` file, it cannot be absolute, and it cannot use
`..` to climb out. A symlink that resolves outside `app/` is rejected too.

If there is no `.car` directory, `canyonos deploy` falls back to
`config/global_controller.yaml` and an `agents/` directory at the project
root. That is the layout `canyonos new-app` scaffolds.

## What becomes `/app`

Each image is built from a context that starts as a copy of `app/` with
relative paths intact. The build then writes the platform's runtime modules,
the generated stubs and a copy of the service's entrypoint on top of it.
Inside the container the working directory is `/app` and Python starts there,
so `/app/pkg/mod.py` imports as `pkg.mod`. [Images and
dependencies](IMAGES_AND_DEPENDENCIES.md) explains what the copy leaves out
and what gets overwritten.

## What the platform writes outside `app/`

Deploying writes one thing into your files: if the manifest has no
`project_id`, the Global Controller generates a UUID and appends
`project_id: "<uuid>"` to `global_controller.yaml` so it survives restarts.
If the key is present with no value, it fills that line in place.

`canyonos build` runs a coding agent that follows the porting skill. That
procedure may append `.car/` to your `.gitignore` and add key names to
`.env.example`. Nothing in the runtime touches `.env`: it is only read, as the
file `env_file` points at.

## What `.env` is for

`env_file` in the manifest names a file, normally `.env` at the project root,
that Docker passes to every container with `--env-file`. Put API keys and any
other secrets your code reads there. Do not put model provider base URLs in
it: the runtime sets those itself and its values win over the file. See
[LLM gateway](LLM_GATEWAY.md).

Never copy a secret into `.car/app`. The image sweep would bake it into every
image. The sweep does drop PEM private keys, `.p12`, `.pfx` and `.jks` files
and prints a warning for each, but it cannot recognise a key written into a
Python string or a JSON file.
