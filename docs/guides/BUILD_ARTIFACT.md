# Project layout

Every `canyonos` command works from a project root. If the folder you run it
from has a `.canyon` folder, `.canyon` is the root; otherwise the folder itself
is. No project file outside the root is read. `canyonos convert` writes its
result into `.canyon`, so a converted project runs from there and the original
source beside it is not part of the deployment. The one exception is `.env`,
which stays in the folder you run `canyonos` from and never goes inside
`.canyon`. Every path in these docs is relative to the root.

## Names

CanyonOS Core is the product. `canyonos` is the CLI. Inside the platform the
Python package is `canyonos_core`, environment variables start with
`CANYONOS_`, and Docker images and containers are named
`canyonos-<project>-*`, where `<project>` is the normalised name of the folder
`canyonos` runs from plus the first 8 characters of its `project_id`. Image tags
add the lowercased entry name (`canyonos-myapp-3f9a1c2e-splitagent`), and containers are
`canyonos-<project>-<agent>-<replica>`.

## Layout

```text
config/
  global_controller.yaml   deployment manifest
  policy.yaml              optional access rules
...                        your application code, becomes /app
stubs/                     generated by the build
grpc_stubs/                generated by the build
docker_container/          generated by the build, one context per image
```

You author `config/` and the code. The build generates the other three
inside the Global Controller container's copy of the root, not in your folder.
These four names are reserved at the top of the root, so `canyonos convert`
refuses a source folder that has any of them. `canyonos clean` deletes `.canyon`
if there is one, and removes the local Docker image of each agent listed in
`config/global_controller.yaml`.

Every path in the manifest (`entrypoint`) is relative to the root. It has to be
a `.py` file, it cannot be absolute, and it cannot use `..` to climb out. A
symlink that resolves outside the root is rejected too.

## What becomes `/app`

Each image is built from a context that starts as a copy of the root with
relative paths intact, minus `stubs/`, `grpc_stubs/` and `docker_container/`.
The build then writes the platform's runtime modules, the generated stubs and a
copy of the agent's entrypoint on top of it.
Inside the container the working directory is `/app` and Python starts there,
so `/app/pkg/mod.py` imports as `pkg.mod`. [Images and
dependencies](IMAGES_AND_DEPENDENCIES.md) explains what the copy leaves out
and what gets overwritten.

## What the platform writes into your files

Deploying writes one thing into your files: the first `canyonos deploy` adds
`project_id: <uuid>` to `config/global_controller.yaml` in the root. Every later
deploy reuses it, so the project stays one project on the dashboard. Deleting
that line starts a new one, and so does `canyonos clean` on a converted project,
because it deletes `.canyon` and the manifest with it.

`canyonos convert` runs a coding agent that follows the porting skill. That
procedure may append `.canyon/` to your `.gitignore` and list the credential
names the code needs in `.canyon/.env.example`. Nothing in CanyonOS writes or
deletes `.env`: it is only read.

## What `.env` is for

`.env` lives in the folder you run `canyonos` from. `canyonos deploy` copies it
into the Global Controller's `/workspace`, which reads it for `${VAR}` references
in the manifest and for cloud credentials, and passes it to each agent replica
with `--env-file`. The endpoint, Redis and metrics-collector containers do not
get it. Put API keys and any other secrets your code reads there. Do not put
the Bedrock endpoint URL or the proxy variables in it: the runtime sets those itself and its values win over the file. See
[LLM gateway](LLM_GATEWAY.md).

Hidden files such as `.env` never reach an image. Never put any other secret in
the root: the image sweep would bake it into every image. The sweep does drop
PEM private keys, `.p12`, `.pfx` and `.jks` files
and prints a warning for each, but it cannot recognise a key written into a
Python string or a JSON file.
